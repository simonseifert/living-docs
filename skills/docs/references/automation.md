# Background jobs and the inbox

Loaded by `/docs absorb`, or when checking what the nightly jobs did.

## Absorb: facts flagged elsewhere

If other pipelines or your own notes leave lines in a markdown notes folder (`$VAULT_DIR`, default `~/vault`) that mention `docs-reference` or carry an `other:docs-reference` tag. `scripts/inbox.py` (free, runs nightly before the refresh) collects new ones into `<library>/_inbox/pending.md` as a checklist with source path:line, context, URLs and a guessed tool. `/docs absorb` = go through that list: for each item, open the source note, decide if it holds a real, sourced fact for an existing brief (patch that section, add the URL to `sources.yaml`, log it in `history.md`), a reason to build a new brief (note it, ask the user), or nothing (many hits are just mentions of the library path). Delete each item from pending.md once handled. Commit as `docs: absorb <n> items`.

## Nightly auto-refresh (free, local GPU)

`scripts/refresh_batch.py` is meant for a nightly timer (systemd or launchd) on a machine with Ollama, e.g. `--max 60 --time-budget-min 150 --commit`, plus a weekly `--all-tools` sweep so unused tools do not rot either. It runs `detect.py`, picks sections (tools whose detector moved first, then stale sections of tools used in the last 30 days, oldest first), fetches each with `reach`, reads registry versions directly (no model) and otherwise compares with the local model via `groq_refresh.py --provider local`, auto-applies only checkable number-level edits and queues everything else for `/docs review` (see below), restamps only when the fetched page actually contained the section's facts, rejects any patch that adds instruction-like text or a URL found in neither the old section nor the fetched page (pages are untrusted input), logs to `history.md` + `CHANGELOG.md`, commits, unloads the model and sends one ntfy summary. Set `DOCS_SHARED_MODEL` to the model your GPU keeps resident for every tool to use it as is (never unloaded), or `DOCS_GPU_YIELD_TO=<model-prefix>` to make it wait while another resident model on the same GPU was used in the last few minutes. Run log: `<library>/_state/refresh-<date>.json`. To review what it did: `git log --author-date-order -- <tool>/` or `git show` on the `docs: auto-refresh` commits; `git revert` any bad one. Sections map to brief headings by an explicit `heading:` key in sources.yaml if present, else a cached pick, else token overlap, else a local-model pick (a wrong pick cannot do harm: nothing is patched or restamped unless the fetched page contains the old section's own facts). Add a `heading:` key when you see a section mis-mapped in a run log. **Major releases first:** a version watcher can append a JSON line (`{"tool", "new_version", "old_major", "source"}`) to `$DOCS_MAJOR_FEED` (default `<library>/_inbox/majors.jsonl`) when a tool with a brief ships a new major version. Each unseen (tool, version) puts all of that tool's sections at the front of the next run (within the half-run cap), writes `_review/<tool>--major-<version>.md` (a major release needs a real rewrite, which number-only patches cannot do) and leads the ntfy summary with `NEW MAJOR`. Seen pairs live in `_state/major-bumps.json`; `DOCS_MAJOR_FEED` overrides the feed path. A manual `/docs refresh` is still the path for sections it marks `unverified`, `fetch-failed`, `rejected-patch` or `no-heading-match`.

## Review queue (`/docs review`)

The nightly job only auto-applies edits it can check mechanically: a version read straight from a registry (npm, PyPI, GitHub latest release, WordPress plugin API) when the section names exactly one version, or a model patch that changes only numbers on existing lines with every new number present on the fetched page. Anything else (new bullets, rewritten prose, a section naming several versions) is written to `<library>/_review/<tool>--<section>.md` with the current text, the proposal, the source URL and why it was queued. `/docs review` = for each file: open the source, verify every claim in the proposal (the proposal came from a 20B local model and can be wrong or invented), apply what checks out to `brief.md` by hand, restamp that section in `sources.yaml`, log it in `history.md`, delete the file. Commit as `docs: review <n> proposals`. Never apply a proposal unverified.

## Weekly freshness ping

`scripts/docs_freshness.py` runs `stale.py` and sends ONE ntfy notification with the most-overdue tools (capped at 12 lines; ntfy turns bodies over 4 KB into attachments). Model-free, zero cost, skips live `status` sections by default. Point it at an ntfy config (see `examples/ntfy.example.json`) via `$DOCS_NTFY_CONFIG` or `~/.config/docs/ntfy.json`, then schedule it weekly with launchd or cron. Prefer a self-hosted or access-controlled ntfy: on public ntfy.sh anyone who knows the topic can read the messages, and they name your tools. Refreshing stays a choice: the ping tells you which tool to run `/docs refresh` on.
